# Автоматизации Gitelman на GitHub Actions (замена n8n)

В этом репозитории живут несколько задач, заменивших n8n-воркфлоу. Все они работают
с одной месячной Google-таблицей (`SPREADSHEET_ID`) и общими секретами.

| Задача | Файл | Расписание | Что делает |
|---|---|---|---|
| Выгрузка сделок amoCRM | `amo_export.py` | 01:10 МСК | сделки+контакты amoCRM → лист «общая выгрузка от Никиты» |
| Выгрузка звонков | `pbx_export.py` | 01:15 МСК | звонки OnlinePBX за месяц → лист «…ЗВОНКИ» |
| Публикация отчётов в ТГ | `tg_report.py` | после выгрузки amoCRM | читает лист `tg_reports` и шлёт готовые тексты в Telegram |
| Контакты+сделки 2-й линии | `second_line.py` | 01:20 МСК | целевые контакты с 01.01.26 + их сделки → отдельная таблица 2-й линии |
| Транскрибация зумов | `zoom_transcribe.py` | 22:20 МСК | записи Zoom → Apify+Deepgram → Google Doc, ссылка в лист «дпд» |
| Напоминание о новой таблице | `monthly_reminder.py` | 1-го числа 09:00 МСК | просит в ТГ завести таблицу на новый месяц |
| Заявки на оплату сервисов | `service_payments.py` | за 5 раб. дней до 5-го числа | режет расходы ОП по отделам и шлёт в ТГ ссылки на предзаполненную гугл-форму (см. ниже) |

> ⏰ **Запуск по расписанию идёт извне** — через сервис cron-job.org, который дёргает
> GitHub API в нужное время. Собственный cron GitHub на этом репозитории отключён:
> на новом репо он срабатывал ненадёжно и не в своё время. Все воркфлоу по-прежнему
> можно запустить вручную (вкладка Actions → Run workflow). Настройка внешнего
> триггера описана в `EXTERNAL_TRIGGER.md`.

> ⚠️ `second_line.py` пишет в **отдельную** таблицу (`1_cI3G94U…`, листы «контакты второй линии» и
> «сделки второй линии»), а не в месячную. Этой таблице тоже нужно дать доступ Редактора
> сервис-аккаунту `clode-60@amo-export-500512.iam.gserviceaccount.com`.

> «Публикация отчётов» не имеет своего времени — она запускается автоматически сразу
> после успешного завершения выгрузки amoCRM (триггер `workflow_run`).

Каждая — отдельный workflow в `.github/workflows/`. Ниже подробно про основную (amoCRM);
остальные устроены так же (секреты те же, плюс `ONLINEPBX_AUTH_KEY` для звонков).

## Выгрузка amoCRM → Google Sheets

Замена n8n-воркфлоу **«Амо выгрузка авто»**. Делает ровно то же самое: раз в день
собирает сделки трёх воронок из amoCRM (за последние 3 месяца), обогащает их данными
контактов и пишет в Google-таблицу. Только теперь это обычный Python-скрипт, который
бесплатно крутится на **GitHub Actions** по расписанию.

> Цель этого README — чтобы вы могли **сами** менять расписание, чинить ошибки и
> понимать, что происходит, без обращения к Claude Code.

---

## 1. Как это устроено (общая картина)

```
GitHub Actions (по расписанию 22:00 МСК)
        │
        ▼
  amo_export.py  ──►  amoCRM API   (тянет сделки + контакты)
        │
        └──────────►  Google Sheets API   (чистит и пишет таблицу)
```

Никакого сервера нет. GitHub бесплатно запускает виртуальную машину, ставит Python,
выполняет скрипт и выключает её. Вы платите $0.

**Что делает скрипт по шагам** (видно в логах при запуске):
1. Считает период: со «вчера минус 3 месяца» по «вчера» (по Москве).
2. Тянет справочники: пользователи, воронки и этапы.
3. Постранично тянет сделки воронок `8733326, 9701010, 7295078`.
4. Разворачивает каждую сделку в строку таблицы (~70 колонок, кастомные поля — по названиям).
5. Догружает основные контакты сделок и дополняет строки (телефон, tg, должность, ниша…).
6. Чистит старые строки в таблице и записывает свежие.

## 3. Разовая настройка (делается один раз)

### Шаг 1. Создать репозиторий на GitHub
1. Создайте новый **приватный** репозиторий (например `amo-export`).
2. Залейте туда содержимое этой папки. Из терминала в папке `amo-export`:
   ```bash
   git init
   git add .
   git commit -m "amoCRM → Sheets export"
   git branch -M main
   git remote add origin https://github.com/<ваш-логин>/amo-export.git
   git push -u origin main
   ```

### Шаг 2. Получить токен amoCRM
Нужен **долгоживущий токен** интеграции (long-lived token):
- amoCRM → **Настройки → Интеграции → Создать интеграцию** (или открыть существующую) →
  вкладка **«Ключи и доступы»** → скопировать **долгосрочный токен**.
- Этот же токен сейчас лежит в n8n в кредле **«amoCRM Header Auth»** — можно взять оттуда.

Скрипт шлёт его как заголовок `Authorization: Bearer <токен>`.

### Шаг 3. Сделать сервис-аккаунт Google (для записи в таблицу)
Сервис-аккаунт = «робот-почта», которому дают доступ к таблице. Это надёжнее OAuth для
автозапуска.
1. [Google Cloud Console](https://console.cloud.google.com/) → создайте/выберите проект.
2. **APIs & Services → Library** → найдите **Google Sheets API** → **Enable**
   (⚠️ обязательно включить — у нас уже была проблема, что у сервис-аккаунта Sheets API был выключен).
3. **APIs & Services → Credentials → Create credentials → Service account** → создайте.
4. У созданного аккаунта → вкладка **Keys → Add key → Create new key → JSON** → скачается файл.
5. Откройте JSON, найдите поле `"client_email"` (вида `xxx@xxx.iam.gserviceaccount.com`).
6. Откройте целевую Google-таблицу → **Настройки доступа** → дайте этому email права
   **Редактор**.

### Шаг 4. Положить секреты в GitHub
В репозитории: **Settings → Secrets and variables → Actions → New repository secret**.
Создайте два секрета:

| Имя секрета | Значение |
|---|---|
| `AMO_TOKEN` | токен из Шага 2 |
| `GOOGLE_SERVICE_ACCOUNT_JSON` | **всё содержимое** скачанного JSON-файла (скопировать целиком) |
| `TELEGRAM_BOT_TOKEN` | *(необязательно)* токен бота от @BotFather — для уведомлений |
| `TELEGRAM_CHAT_ID` | *(необязательно)* id чата/канала, куда слать отбивку |
| `ONLINEPBX_AUTH_KEY` | для выгрузки звонков (auth_key интеграции OnlinePBX) |
| `APIFY_TOKEN` | для транскрибации зумов (токен Apify) |
| `DEEPGRAM_TOKEN` | для транскрибации зумов (ключ Deepgram) |

> Для транскрибации зумов сервис-аккаунту нужны **Google Docs API** и **Google Drive API**
> (включить в Cloud), а также доступ Редактора к таблице «маркетинг» `1gbj-…` и папке
> Google Drive `1F_Sdc…` (где создаются доки с транскриптами).

Ещё одна **переменная** (Settings → Variables, не секрет): `SPREADSHEET_ID` — id месячной таблицы, общей для всех трёх задач. Меняется в один клик каждый месяц.

> Телеграм-секреты необязательны: если их не задать, скрипт просто не шлёт уведомления.
> Узнать `TELEGRAM_CHAT_ID`: напишите боту любое сообщение, затем откройте
> `https://api.telegram.org/bot<ТОКЕН>/getUpdates` — там в `chat.id` будет нужное число
> (для канала добавьте бота в админы и используйте `@имя_канала`).

### Шаг 5. Проверить
В репозитории: вкладка **Actions** → workflow «amoCRM → Google Sheets» →
**Run workflow** (ручной запуск). Откройте запущенный прогон и смотрите логи.
Если в конце `ГОТОВО. Записано строк: N` — всё работает. Дальше пойдёт по расписанию само.

## 4. Как управлять (самое нужное)

### Поменять расписание
Файл `.github/workflows/amo-export.yml`, строка `- cron: '0 19 * * *'`.
- Формат: `минуты часы * * *`, **время в UTC** (Москва = UTC + 3).
- Примеры: `0 19 * * *` = 22:00 МСК · `0 6 * * *` = 09:00 МСК · `30 5 * * 1` = 08:30 МСК по понедельникам.
- После правки — закоммитить и запушить. [Помощник по cron](https://crontab.guru/).

### Запустить вручную
Вкладка **Actions** → выбрать workflow → **Run workflow**. Удобно для проверки.

### Посмотреть, что пошло не так
Вкладка **Actions** → красный (упавший) прогон → шаг **«Запустить выгрузку»** →
читать вывод. Скрипт печатает каждый этап и понятную ошибку.

### Поменять настройки выгрузки
Всё в начале `amo_export.py`, блок **НАСТРОЙКИ**:

| Настройка | За что отвечает |
|---|---|
| `PIPELINE_IDS` | какие воронки выгружать |
| `MONTHS_BACK` | за сколько месяцев брать сделки (сейчас 3) |
| `SPREADSHEET_ID` / `SHEET_NAME` | таблица и вкладка назначения |
| `HEADER_ROW` | строка с заголовками колонок (сейчас 2) |
| `DATA_START_ROW` | с какой строки писать данные (сейчас 15) |
| `EXPORT_DATE_CELL` | ячейка для даты выгрузки (пусто = не писать) |

## 5. Частые проблемы

| Симптом в логах | Причина и решение |
|---|---|
| `amoCRM 401` | Протух/неверный `AMO_TOKEN`. Обновить токен в amoCRM и в Secrets. |
| `403` от Google / `PERMISSION_DENIED` | Не дали сервис-аккаунту доступ к таблице (Шаг 3.6) или не включили Sheets API (Шаг 3.2). |
| `Не нашёл заголовки в строке 2` | Сменили вёрстку таблицы. Поправить `HEADER_ROW` / `SHEET_NAME`. |
| Данные легли не на ту строку | Поправить `DATA_START_ROW`. |
| Пустая выгрузка (`строк после фильтра: 0`) | За период нет сделок, либо сменились `PIPELINE_IDS`. |
| Колонка не заполнилась | В таблице заголовок (строка 2) не совпадает по тексту с именем поля. Сопоставление идёт по точному названию колонки. |

## 6. Важные нюансы GitHub Actions

- **Расписание не идеально точное.** GitHub может запустить cron с задержкой 5–15 минут
  (иногда больше) в часы пиковой нагрузки. Для суточной выгрузки это не критично.
- **Сon отключается после 60 дней без активности** в репозитории. Любой коммит сбрасывает счётчик;
  ручной запуск раз в пару месяцев тоже подойдёт.
- **Бесплатно:** приватный репозиторий даёт 2000 минут/мес, наш прогон — пара минут в день.
  Публичный — без лимита.
- Cron работает только в ветке по умолчанию (`main`).

## 7. Чем отличается от n8n-версии (для сверки)

Логика идентична. Сделано чуть аккуратнее в двух местах:
- Пользователи тянутся постранично (в n8n бралась только первая страница) — на случай >250 сотрудников.
- `Дата изменения` сразу пишется текстом `дд.мм.гггг чч:мм:сс`, `Причина отказа` — названием
  (в n8n это делалось отдельной нодой «Fix fields» — здесь объединено).

Запись в таблицу: скрипт читает заголовки из строки 2, чистит старые данные и пишет новые
с `DATA_START_ROW`. Если в вашей таблице строки 3–14 заняты формулами/шапкой — они не трогаются.

## Заявки на оплату сервисов (`service_payments.py`)

Автоматизирует ежемесячную подачу заявок на оплату сервисов отдела продаж через гугл-форму
«Добавить новую заявку». Работает с таблицей **«Ежемесячные расходы ОП»**
(`1nbeuUG1IPAMcj-uBmI7grCzHTSdlKTy4BD5sCuxIGyw`), не с месячной таблицей выгрузок.

**Что остаётся ручным:** вписать суммы месяца в колонку главного листа (как и раньше), получить
согласование, в каждой заявке приложить скриншот и нажать «Отправить». Файл в форму ссылкой
передать нельзя — это ограничение Google Forms.

**Что делает скрипт:**
1. Берёт колонку месяца оплаты на главном листе (самая правая с таким названием).
2. Делит каждую сумму по отделам, статья в форме = отдел:
   - «Баланс телефонии» — доли из «Телефония расход» `K22:K24` (80/20), комиссия банка из `L31` (5 %) уходит в прочее;
   - «АТС online PBX» — блок «Телефония расход» `I4:K9` (запись звонков → прочее);
   - «Wazzupp Whatsupp…» — блок «Wazzup расход» `L4:N25` даёт доли отделов, заявка в **AED**. Сумма — из ячейки «Wazzup расход» `R17` («счёт AED», итог счёта с НДС), если заполнена; пустая → рубли из главного листа по курсу из `R16` («курс aed») или курсу дня. При ручном запуске курс можно задать полем `aed_rate`;
   - «ZOOM» — блок «Zoom расход» `J17:K19`;
   - «Cloude» — $100 переводится в рубли по курсу из `B29` главного листа (там формула GOOGLEFINANCE), иначе курс дня;
   - VPN, Сервер, Telegram Premium, Marquiz, Виджет триггеры — целиком в прочее; WABA и S3 — в 1-линию;
   - «AMOcrm» — пропускается (платится раз в год).
   Правила лежат в `RULES` в начале скрипта — менять там.
3. Пишет лист **«Заявки»** в той же таблице: колонка A «Подано» — флажки, которые ставишь руками по ходу подачи; при повторном запуске за тот же месяц галочки сохраняются, другие месяцы не трогаются. Для валютных заявок колонка «Курс: валюта за 1 ₽» редактируемая и записана как в банке (1 ₽ = 0,011339 $): «Сумма заявки» и «Ссылка на заявку» — формулы, они пересчитываются от курса прямо в таблице (если сумма взята из счёта, от курса пересчитываются только рубли). Ячейки курса в таблице (`R16`, `B29`) и поля запуска принимают оба формата: число меньше единицы считается курсом за 1 ₽.
4. Шлёт в Telegram два сообщения: свод на согласование (для пересылки опер-диру) и список ссылок
   на форму с уже заполненными полями — по одной ссылке на каждую заявку.

Сверки: если блок по отделам не сходится с суммой на главном листе, или сервис был в прошлом
месяце, а сейчас пустой, — скрипт пишет предупреждение в свод.

**Настройка:** таблице нужен доступ Редактора для `clode-60@amo-export-500512.iam.gserviceaccount.com`
(лист «Заявки» создаётся сам). Переменные (необязательно): `SERVICES_SPREADSHEET_ID` — другая таблица,
`SERVICE_PAY_CHAT_ID` — чат для заявок (по умолчанию `TELEGRAM_CHAT_ID`).

**Запуск:** плановый — ежедневно 09:00 МСК с 24-го по 31-е, реально отрабатывает только в день
«5 рабочих дней до 5-го числа». Ручной — Actions → «Заявки на оплату сервисов» → Run workflow,
можно указать месяц `YYYY-MM`, курсы и режимы: «только лог», «только ссылки» (повтор без свода и таблицы), «только таблица» (обновить лист без Telegram). Локально:
`SHEETS_LOCAL_DIR=<папка с csv листов> DRY_RUN=1 PAY_MONTH=2026-10 python service_payments.py`.

## Телефония по отделам (`telephony_split.py`)

Считает, сколько каждый отдел реально потратил у BMI за месяц, и кладёт итог на лист
«Телефония расход» таблицы «Ежемесячные расходы ОП» от `O21` (правее — свободная область).

**Как считает.** Каждый исходящий звонок из экспорта BMI (`/stats/calls/export`, время в UTC)
ищется в истории OnlinePBX по номеру назначения (последние 10 цифр) и времени (±4 мин); так
узнаём внутренний номер менеджера, а по листу «Телефония расход» A:G (колонка F «Отдел») — отдел.
Платные звонки (цена в экспорте BMI; пустая цена = внутри пакета) относятся на отдел менеджера.
Абонентка = акт BMI за месяц (`/documents?type=act`) − платные звонки; делится по доле звонков отдела.
Не найденные в АТС звонки делятся так же. Если акта ещё нет (месяц не закрыт),
абонентка берётся по текущему тарифу как оценка — это написано в колонке «Акт BMI ₽».

**Результат.** Две таблицы Google на листе (созданы Никитой через «Преобразовать в таблицу», скрипт пишет
внутрь них и подгоняет границы): сводка — строка «факт» по каждому месяцу и строка «прогноз» на следующий
месяц (факт по отделам, округлённый вверх до 1 000 ₽), и таблица по менеджерам (звонки, минуты, платных
звонков, платные ₽). Абонентка делится по доле звонков отдела; номер без отдела → прочее.

**Запуск.** Только вручную: Actions → «Телефония по отделам (BMI × АТС)», месяцы `YYYY-MM` через
запятую (пусто = прошлый месяц), галка «только лог». Список сотрудников правится на листе: добавил
номер и отдел — следующий запуск учтёт. Трёхзначные номера без отдела попадают в строку «без отдела».
